# Registro de actividad + contraseñas — Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: superpowers:executing-plans (native, chosen for previous plans). Steps use `- [ ]`.

**Goal:** Admin "Actividad" page backed by an `activity_log` table fed from user, invoice, assignment and service actions (1-year retention); stronger rules for new passwords.
**Architecture:** One non-throwing `logActivity()` helper called after each successful mutation; admin list endpoint with filters; frontend page with filters and details. `validatePassword()` shared by every password-setting endpoint.
**Tech Stack:** Node/Express/pg/node:test (local `guru_test`), React/TS/vitest.
**Spec:** `docs/superpowers/specs/2026-09-27-activity-log-passwords-design.md`

## Global Constraints
- `logActivity` must never throw nor delay the response noticeably (await with catch; errors only logged).
- Categories exactly: `usuarios`, `facturas`, `asignaciones`, `servicios`, `seguridad`. Summaries in Spanish, human readable, include amounts as `RD$` with `es-DO` formatting.
- Never store passwords, tokens or Turnstile tokens in `details`.
- Retention 365 days; purge on startup and every 24 h.
- Password rule: ≥ 8 chars, ≥ 1 letter, ≥ 1 digit, not in common list (case-insensitive), must not contain username or any name word ≥ 3 chars (case/accents-insensitive). Error code `WEAK_PASSWORD`, 400, Spanish message explaining the failed rule.
- Existing passwords are never re-validated (login unaffected).
- Backend tests only on local DB.

## Review Focus
- A logging failure (e.g. table missing before migration) must not break the action (Task 2 test with table dropped).
- Admin filters by a person → only that person's actions; pagination stable (ORDER BY created_at DESC, id DESC).
- Temporary passwords generated by the UI must satisfy the backend policy (Task 6 test on generator × validatePassword rules).
- Failed login logging must not reveal whether the username exists to the caller (response unchanged).
- Details never contain `password`, `temp_password`, `currentPassword`, `newPassword`, `turnstileToken`.

## Task 1 (BE): migration `20260927_activity_log.sql` + test
Table/indices per spec; idempotent (`IF NOT EXISTS`). Test: runs twice; insert works; indices exist.

## Task 2 (BE): `src/services/activityLog.js` + tests
- `logActivity(req, { category, action, entityType, entityId, summary, details })` inserts with `actor_id = req?.user?.id ?? actor?.id ?? null`, `actor_name` = DB name lookup is NOT needed — use `req.user.username` fallback; `ip = req?.ip`. Strips sensitive keys recursively from `details`. Catches all errors.
- `listActivity({ category, actorId, from, to, q, page=1, pageSize=50 })` → `{ items, total }`; joins `users` for current `color, avatar, name`.
- `purgeOld(days=365)` → deleted count; `startActivityRetention()` uses `setInterval(..., 24h).unref()`.
- Tests: insert + list filters (category, actor, date range, q ILIKE on summary), pagination order, sensitive keys stripped, missing table → no throw, purge removes >365 days only.

## Task 3 (BE): `src/config/passwordPolicy.js` + tests
`validatePassword(pw, { username, name })`. Tests: short, no digit, no letter, common ("12345678", "password1", "guru2024"), contains username ("hengi123"), contains name word ("Pedro Gómez" → "gomez2026" rejected), valid ("Casa2026x").

## Task 4 (BE): apply policy
change-password, admin create + temp-password, register → 400 `WEAK_PASSWORD`. Update existing tests that use weak passwords ('temp123', 'nueva123', 'another1', 'otra123'…) to policy-compliant values where they hit these endpoints. Tests: each endpoint rejects "12345678".
